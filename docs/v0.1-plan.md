# Version 0.1 plan

## Goal

Provide a portable, inspect-first workflow that can establish a minimal engineering harness at project start or retrofit one into an existing repository without imposing a specific language, formatter, CI provider, or agent vendor.

## Included

- Detect common ecosystems, lockfiles, repository instructions, quality configuration, CI, hooks, and package verification scripts.
- Classify repositories as greenfield or brownfield from observable source files.
- Guide agents through navigation, knowledge, executable checks, one verification command, CI, optional hooks, and governance boundaries.
- Package the workflow as a valid `bootstrap-project-harness` Skill.
- Preview or create a minimal `AGENTS.md`; require explicit `--apply` and never overwrite existing files.
- Verify behavior on Windows, Linux, and macOS using only Python's standard library.

## Excluded

- Mutating a target repository from the audit script or without explicit generator apply mode.
- Generating every possible configuration from a universal template.
- Installing dependencies or hooks without explicit approval.
- Creating repositories, changing branch rules, managing secrets, deploying, committing, or pushing.
- Autonomous orchestration, background agents, and hosted services.

## Automated acceptance

- `python scripts/verify.py` succeeds.
- Greenfield, TypeScript brownfield, malformed manifest, and ignored-directory fixtures behave deterministically.
- The distributable Skill has valid frontmatter, matching directory name, UI metadata, and no repository-level documentation inside its package.
- CI runs the same verification command on Windows, Linux, and macOS.

## Human acceptance

- The README explains the boundary without promising enforcement that repository files cannot provide.
- The Skill produces a proportionate proposal for at least one empty repository and one established repository.
- GitHub repository visibility, description, topics, branch protection, private vulnerability reporting, and initial release are configured by a maintainer.

## Later candidates

- Fixture-backed proposal snapshots for more ecosystems.
- Optional generator modules with explicit dry-run and diff output.
- Agent-vendor adapters that point to one canonical contract.
- Release packaging and installer integrations.
